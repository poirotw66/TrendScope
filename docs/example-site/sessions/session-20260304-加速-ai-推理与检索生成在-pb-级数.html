1. 會議概述和核心內容

會議背景： 本次主題演講隸屬於 2025 年的 AiCon Beijing 全球人工智能開發與應用大會，由極客邦科技主辦，旨在探討人工智能領域的最新技術發展與應用。演講內容緊扣 AI 時代對數據處理效能的極致要求，特別是針對大型語言模型（LLM）、AI Agent、線上特徵儲存等核心 AI 場景對數據湖的即時訪問需求。

核心問題與挑戰： 演講首先點出了當前數據密集型 AI 應用所面臨的核心挑戰：如何在 PB 級（數十至數百 PB）的、基於物件儲存（如 S3）且採用 Iceberg 表格式（底層為 Parquet 文件）的數據湖上，實現 SELECT ID, DATA FROM TABLE WHERE ID = 123 這種點查詢達到亞毫秒級的響應時間。

現有方案的局限性被明確指出： * 傳統 OLAP 引擎： 對於簡單的點查詢而言過於重量級，存在查詢規劃、排程和全文件掃描等開銷，導致高延遲（通常數百毫秒）。 * 記憶體 KV 儲存： 雖然能提供低延遲，但在 PB 級數據規模下成本極其高昂，且需要複雜的 ETL 管線進行數據同步，引入數據延遲和一致性問題（即「雙儲存問題」），增加了操作複雜性。 * 原生「S3 上的 Parquet」： 由於多次 S3 物件儲存往返時間（RTTs）和行組/頁解碼開銷，其 p95 延遲通常超過 300 毫秒，遠不能滿足亞毫秒級需求。

2. 技術要點和實現細節

Alluxio 實現這一突破的關鍵在於其「Meet-in-the-Middle」的架構理念，以及針對大規模數據湖和 Parquet 格式進行的深度性能工程。

2.1 Alluxio 基礎架構與理念： * Meet-in-the-Middle 理念： Alluxio 不偏向於「將數據移動到計算」或「將計算移動到數據」，而是提供一個數據專用的共享快取層，讓計算與儲存在此相遇。這個快取由多個應用程式共享，而非應用程式專用，從而避免了數據冗餘和管理複雜性。 * 統一儲存介面： Alluxio 作為一個邏輯文件系統，能夠將多種底層儲存服務（如 HDFS、S3）掛載到統一的命名空間，為上層應用提供無縫的數據訪問體驗。 * 可擴展的分布式快取： 作為一個分布式快取層，Alluxio 能為 Spark、Presto、TensorFlow 等多種應用程式加速數據訪問。數據透過一致性哈希分散快取到多個 Alluxio Worker 節點上。

2.2 低延遲文件訪問基礎： Alluxio 為其上層的 Parquet 查詢優化奠定了堅實的低延遲文件訪問基礎，使得從快取中隨機讀取約 1KB 文件可達到約 ~1 毫秒的訪問時間。關鍵技術包括： * 異步事件循環 (Asynchronous Event Loop)： Alluxio Worker 建立在高性能的非阻塞異步 I/O 框架上，減少了上下文切換和線程爭用，單個 Worker 實例能擴展到數千個併發連接。 * NVMe 上的堆外頁面儲存 (Off-Heap Page Storage on NVMe)： Alluxio 利用高性能 NVMe SSD 儲存堆外快取頁面。堆外儲存避免了 Java 垃圾回收（GC）的開銷，而 NVMe 提供了極低的訪問延遲和高吞存量，在成本和性能之間取得最佳平衡。 * 零拷貝 I/O (Zero-Copy I/O)： 透過使用 sendfile() 和 mmap() 等操作系統級技術，Alluxio 避免了數據在用戶空間和內核空間之間不必要的記憶體拷貝，顯著降低了 CPU 負載，提升了數據傳輸吞吐量和降低延遲。

2.3 針對 Parquet 點查詢的深度優化： 在上述基礎之上，Alluxio 針對 Parquet 點查詢的特性進行了進一步的創新性優化： * 問題診斷： 最初將 ParquetReader API 應用於 Alluxio 快取文件，雖然性能有所提升（從 S3 的 411 毫秒降至 46 毫秒），但仍遠未達到亞毫秒級。透過火焰圖分析，發現大量的 CPU 時間花費在 org/apache/parquet 相關的解碼和 io/netty 網絡 I/O 操作上，證明標準 ParquetReader 對點查詢過於重量級。 * 利用 Parquet 結構加速： Alluxio 深度理解並利用 Parquet 文件的內部結構來加速查找： * Footer (文件尾)： 包含每個行組（RowGroup）的列統計信息（如 id 列的最小值和最大值），允許 Alluxio 快速透過二分查找定位到包含目標 id 的正確行組。 * Column Index (列索引)： 在選定的行組內部，利用列索引定位到包含正確 id 的數據頁（Page），並確定該頁和該行組中的行號。 * Offset Index (偏移索引)： 根據已找到的行號，快速獲取同一行中其他所需列的數據偏移量。 * 關鍵優化思路： * 在 Alluxio 中快取 Parquet 元數據： 將 Parquet 文件的 Footer、Column Index 和 Offset Index 這些關鍵元數據直接快取在 Alluxio 中。這極大地減少了對底層 S3 的多次讀取和複雜的元數據解析開銷，使得對索引的訪問幾乎在 Alluxio 內部完成。 * 將處理負載卸載到客戶端： Alluxio Worker 不再在伺服器端對 Parquet 頁面進行完整的解碼，而是將整個（通常較小且已壓縮的）數據頁面連同其偏移量發送回客戶端。客戶端接收到原始位元組（例如 Protobuf 格式）後自行解碼。這種設計將 CPU 密集型的解碼工作從快取節點轉移到客戶端，降低了快取層的 CPU 負載，以少量網絡開銷換取了更高的快取節點併發性和整體效率。

2.4 疊代優化成果： 透過上述一系列優化，Alluxio 的點查詢延遲實現了顯著的逐步降低： * 基準 (S3)： 411 毫秒 * Alluxio 數據快取： 232 毫秒 * 單一 RPC + Alluxio (數據快取)： 42 毫秒 * 單一 RPC + Alluxio (數據快取 + 元數據快取)： 約 0.297 毫秒

最終達到約 0.4 毫秒的亞毫秒級延遲，成功實現了 1000 倍的性能提升。
